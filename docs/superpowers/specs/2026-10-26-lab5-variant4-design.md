# Дизайн лабораторной работы № 5, вариант 4

## Цель и границы

Подготовить программную часть лабораторной работы по промышленному краулингу на Scrapy для варианта 4. Источник — `https://quotes.toscrape.com`, обход выполняется по тегам с переходом на страницы авторов.

Результат включает полноценный Scrapy-проект, SQLite-базу, JSONL-выгрузку, статистику прогонов, демонстрацию JOBDIR и HTTP-кэша, ноутбук с анализом качества, smoke-check и заполненный отчёт. No-code workflow не реализуется; соответствующий раздел отчёта остаётся шаблоном.

## Ограничение источника и объём

На площадке находятся 100 уникальных цитат, но три из них не имеют тегов и недоступны при обходе варианта 4. Обход по 137 тегам даёт 97 уникальных цитат и 232 уникальные связи «цитата–тег». Поэтому получить 300 уникальных цитат невозможно. Это ограничение явно фиксируется в отчёте.

Требуемый объём представляется нормализованной SQLite-схемой:

- `quotes` — 97 уникальных цитат, доступных через теги, бизнес-ключ `author + quote`;
- `quote_tags` — 232 уникальные связи цитат с тегами;
- всего — 329 содержательных строк.

Повторные появления цитаты на разных страницах тегов проходят через обязательную дедупликацию и не создают повторов в `quotes`. Каждая сохранённая цитата уже содержит полный список тегов, поэтому связи `quote_tags` не теряются после удаления повторов.

## Поток данных

1. `parse_catalog` проходит 10 страниц общего каталога, извлекает все ссылки тегов и планирует страницы тегов.
2. `parse_tag` обходит пагинацию конкретного тега, извлекает цитату, автора и полный список тегов.
3. Для каждой цитаты выполняется `response.follow` на страницу автора. Контекст цитаты передаётся через `cb_kwargs`. Поскольку один автор связан с несколькими цитатами, запрос автора создаётся с `dont_filter=True`; иначе стандартный dupefilter Scrapy оставил бы только первую цитату автора.
4. `parse_author` добавляет дату и место рождения, биографию и создаёт `QuoteItem`.
5. Item проходит четыре pipeline и записывается в JSONL и SQLite.

Scrapy автоматически удаляет повторные запросы одинаковых страниц тегов. Страницы авторов намеренно допускают повторный запрос для каждого контекста цитаты, а повторные элементы, пришедшие из разных тегов, контролируются бизнес-дедупликацией pipeline.

## Паук

Используется обычный `scrapy.Spider`, поскольку переходы между каталогом, тегом и автором имеют разный смысл и требуют явной передачи контекста. `CrawlSpider` с общими правилами усложнил бы разделение уровней.

Паук использует:

- `response.follow` для всех переходов и `dont_filter=True` для запроса автора;
- `cb_kwargs` для передачи цитаты, автора, тегов, исходного тега и страницы списка;
- устойчивые CSS-селекторы по семантическим классам;
- `.get()` и проверки отсутствующих полей;
- `errback` со счётчиками сетевых ошибок;
- `closed()` для сохранения статистики в `stats_<run_id>.json`.

## Item Pipeline

### 100 — ValidationPipeline

Проверяет текст цитаты, автора, URL автора и полный список тегов. При отсутствии обязательного поля увеличивает `dropped/missing_fields` и вызывает `DropItem`.

### 200 — CleanPipeline

Удаляет внешние кавычки и лишние пробелы, нормализует имена тегов, преобразует дату рождения в ISO `YYYY-MM-DD`. Некорректная дата увеличивает `dropped/bad_date` и приводит к `DropItem`.

### 300 — DedupPipeline

Вычисляет бизнес-ключ из нормализованных `author + quote`. Повтор увеличивает `dropped/duplicate` и отбрасывается через `DropItem`.

### 400 — SQLitePipeline

Открывает одно соединение в `open_spider`, создаёт таблицы `quotes` и `quote_tags`, буферизует записи и выполняет пакетные `executemany`. Остаток буфера сохраняется в `close_spider`. Соединение внутри `process_item` не создаётся.

## Настройки и предохранители

В `settings.py` задаются и комментируются:

- `ROBOTSTXT_OBEY = True`;
- учебный `USER_AGENT`;
- общий и доменный лимиты параллелизма, доменный лимит не выше 4;
- `DOWNLOAD_DELAY`;
- `AUTOTHROTTLE_ENABLED` и целевая конкуренция;
- `DOWNLOAD_TIMEOUT`;
- `RETRY_TIMES` и `RETRY_HTTP_CODES`;
- `DEPTH_LIMIT`;
- `CLOSESPIDER_ITEMCOUNT = 300`;
- `HTTPCACHE_ENABLED` для отладочных запусков;
- `LOG_LEVEL` и UTF-8 для Feed Export.

Из-за физического ограничения источника `CLOSESPIDER_ITEMCOUNT = 300` не срабатывает по числу уникальных цитат, но остаётся верхним предохранителем. Итоговый обход завершается после исчерпания очереди. Это объясняется в отчёте.

## JOBDIR и HTTP-кэш

Для JOBDIR выполняется ограниченный первый прогон с сохранением очереди и отпечатков запросов, затем повторный запуск с тем же каталогом. В ноутбуке показываются файлы состояния и `dupefilter/filtered`.

Для HTTP-кэша выполняются два одинаковых ограниченных прогона. Сравниваются время, `httpcache/store` и `httpcache/hit`. Состояние кэша удаляется только перед первым демонстрационным запуском.

## Анализ качества

Ноутбук показывает:

- число строк в обеих таблицах и общий объём;
- уникальность бизнес-ключа;
- полноту каждого поля;
- причины отброшенных элементов;
- распределение HTTP-кодов;
- число запросов, трафик и длительность;
- число цитат и среднее число тегов по авторам;
- самые частые теги и авторов;
- длину цитат и биографий.

`smoke_check.py` сравнивает текущие значения с предыдущей сохранённой сводкой и предупреждает, если число строк упало более чем на 20% или доля пустых обязательных полей превысила 5%.

## Ошибки и проверка

Сетевые ошибки отдельных запросов обрабатываются `errback`, записываются в статистику и не скрываются. Ошибки обязательных полей и типизации оформляются как `DropItem` с отдельными счётчиками.

Проект и ноутбук проверяются глобальным Python 3.10, а не Conda. Успешная проверка включает:

- выполнение итогового паука без необработанной ошибки;
- создание SQLite и JSONL;
- 97 уникальных цитат и 232 связи, всего 329 строк;
- прохождение smoke-check;
- наличие статистики JOBDIR и HTTP-кэша;
- выполнение всех ячеек ноутбука без ошибок.
