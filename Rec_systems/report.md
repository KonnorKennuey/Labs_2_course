## 1. Цель и вариант

Цель — реализовать воспроизводимый сбор через REST API с пагинацией, нормализацией,
обогащением, проверкой качества и инкрементальным сохранением.
Для варианта 4 используются DummyJSON Posts + Comments и ресурс Users для
обогащения. Это разные ресурсы одного сервиса, как предусмотрено вариантом.
Основная таблица содержит одну строку на комментарий: в API 251 пост и
340 комментариев, поэтому требование ≥ 300 уникальных строк выполняется на комментариях.
Целевая задача — анализ активности авторов и связи постов, комментариев и реакций.

## 3. Архитектура и принятые решения

```text
Comments + Posts + Users
  → requests.Session → limit/skip, паузы и повторы → сырые ответы + журнал
  → json_normalize → соединение по ID → типизация и проверки
  → data_clean.csv + state.json → повторный прогон
```

Сессия использует `User-Agent`, `Accept: application/json` и timeout 30 секунд
в каждом запросе. Проверяются статус, Content-Type и корректность JSON;
сообщение об ошибке содержит URL и первые 200 байт тела.
Повторы разрешены только для 429 и 5xx, всего не более четырёх попыток.
Задержка — `2^(attempt−1)` секунд плюс джиттер 0–0,5 секунды,
но не меньше `Retry-After`, если он присутствует. Поддерживаются секунды и HTTP-дата.
Остальные 4xx и сетевые ошибки завершают сбор без повторов.
Перед каждой попыткой установлена пауза 0,3 секунды.

Параметры пагинации: `page_size=100`, `max_records=1000`, `max_pages=20`.
Сдвиг увеличивается на фактический размер страницы; сбор останавливается по
пустой странице, достижению `total` или заданных пределов. Комментарии получены
четырьмя страницами: 100 + 100 + 100 + 40; посты — 100 + 100 + 51;
пользователи — 100 + 100 + 8. Каждый прогон выполнил 10 запросов, все получили HTTP 200.
В журнале фиксируются ресурс, прогон, страница, попытка, URL, параметры, статус,
число записей, длительность запроса и UTC-время.
На имитированных ответах дополнительно проверены повторы 429/5xx, отсутствие
повторов 4xx, предел попыток, оба формата Retry-After и отбрасывание некорректного JSON.

Вложенные объекты развёрнуты через `pandas.json_normalize(sep="_")`.
Массив тегов развёрнут через `record_path="tags", meta=["id", "userId"]`
в `post_tags.csv`. Соединения `comment.postId → post.id` и ID авторов → `users.id`
проверены как `many_to_one`; после каждого соединения осталось 340 строк.
Числовые поля имеют тип `Int64`, даты — datetime с UTC.
Итоговая таблица содержит 20 полей.

Состояние хранит `last_comment_id=340`. Во втором прогоне страницы читаются повторно,
но сохраняются только ID выше водяного знака, отсутствующие в CSV. Новых записей — 0,
число строк осталось 340, дубликатов — 0. Алгоритм рассчитан на возрастающие ID
новых комментариев; изменения и удаления старых записей он не отслеживает.

## 7. Правовая и этическая оценка

DummyJSON позиционирует данные как искусственные для тестирования и прототипирования.
Реальные люди не исследуются. Сведения о вымышленных профилях в рамках этой
лабораторной не рассматриваются как данные определённого реального физического лица.
Поэтому основание обработки персональных данных реальных субъектов здесь не используется.
Критерий персональных данных — связь с определённым или определяемым физическим лицом
(ст. 3 [152-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_61801/)).
Для переноса сбора на реальные профили нужно отдельно определить основание
обработки по ст. 6; публичная доступность сама по себе не заменяет такую оценку.

Для Users выбираются только необходимые поля; пароли, токены, банковские данные,
контакты и адреса не запрашиваются. Выполняются только GET-запросы с паузами,
без обхода авторизации и ограничений. Репозиторий сервиса опубликован под
[MIT-лицензией](https://github.com/Ovi/DummyJSON/blob/master/LICENSE);
при копировании его кода необходимо соблюдать условия лицензии.
Предлагаемый срок хранения учебных выгрузок — до завершения проверки работы,
затем не более 30 дней; это выбранный срок лабораторной, а не требование API.
