# Отчёт по лабораторной работе № 4

## 1. Цель и вариант

**Вариант:** 4.  
**Основной источник:** [ScrapingCourse — JavaScript Rendering](https://www.scrapingcourse.com/javascript-rendering).  
**Проверяемый механизм:** отрисовка каталога JavaScript и извлечение атрибутов карточек.

Цель работы — определить, почему статический HTTP-клиент не получает заполненные данные, реализовать браузерный сбор через Playwright, найти более дешёвый способ получения тех же данных и сравнить подходы по измеренным метрикам.

Контрольный источник `books.toscrape.com` не использовался. Вся программная часть выполнена на учебной площадке ScrapingCourse.

## 2. Как набран требуемый объём

На странице варианта `javascript-rendering` размещено только 12 уникальных товаров. Поэтому использована оговорка задания:

> Если на площадке записей меньше, объём набирается несколькими категориями/страницами/тегами с ведением журнала.

Выбран подход с несколькими страницами и сценариями той же площадки:

| Контекст сбора | Записей | Взаимодействие |
|---|---:|---|
| JavaScript Rendering | 12 | ожидание JS-отрисовки и XHR |
| Pagination | 147 | 13 страниц, переходы по `Next page` |
| Infinite Scrolling | 147 | 17 циклов прокрутки |
| **Итого** | **306** | более пяти циклов |

Единица итогового набора — наблюдение товара в конкретном учебном сценарии. Поэтому один товар, встретившийся в пагинации и бесконечной прокрутке, образует две строки с разным `context`. Композитный ключ `record_id = context + product_key` уникален. Такой способ не скрывается под искусственной дедупликацией: отдельно показаны 147 уникальных товаров и 159 повторных появлений в других контекстах.

## 3. Протокол диагностики источника

| Проверка | Полученный результат |
|---|---|
| Ответ сервера через `requests` | HTTP 200, 29 656 байт HTML |
| Целевые карточки в исходном HTML | 12 элементов `.product-item` |
| Непустые названия в исходном HTML | 0 из 12 |
| Поиск источника данных | В inline-скрипте найден `/ajax/products/json` |
| Fetch/XHR в Playwright | `GET https://www.scrapingcourse.com/ajax/products/json` |
| Ответ XHR | HTTP 200, `application/json` |
| Браузер с JavaScript | 12 заполненных карточек |
| Браузер без JavaScript | 12 заготовок, 0 непустых названий |

Статический парсер видит правильное число контейнеров, но не видит названия и цены. JavaScript после загрузки страницы делает запрос к JSON-эндпоинту и заполняет существующие элементы DOM. Поэтому браузер необходим для воспроизведения поведения страницы и диагностики, но после обнаружения эндпоинта регулярный сбор можно выполнять без браузера.

## 4. Реализация

### 4.1. Playwright

В ноутбуке явно создаются `browser`, `context` и `page`. Контекст получает:

- `user_agent="course-crawler/1.0 (educational use)"`;
- viewport 1280×900;
- locale `ru-RU`;
- таймаут действий 15 секунд;
- таймаут навигации 30 секунд.

Ресурсы закрываются через `async with async_playwright()` и явные `context.close()` / `browser.close()`. После проверочного прогона процессов Chromium и Playwright не осталось.

Для Windows/Jupyter Playwright запускается в рабочем потоке с отдельным `ProactorEventLoop`. Это связано с тем, что event loop ядра Jupyter не поддерживает создание дочернего процесса Playwright. При этом сам сбор остаётся асинхронным.

Данные извлекаются массово через `locator.evaluate_all`. На 12 карточках измерено:

- массовое извлечение: 0,0030 с;
- поэлементные локаторы: 0,0356 с;
- выигрыш массового способа: примерно 12 раз.

### 4.2. Взаимодействия и предохранители

Для пагинации используется семантический локатор `get_by_role("link", name="Next page")`. Выполнено 13 итераций, сбор остановлен на неполной последней странице.

Для бесконечной прокрутки sentinel `#end-of-page` прокручивается в видимую область. После каждой прокрутки код ожидает увеличение числа `.product-item` через `wait_for_function`. Реализованы три предохранителя:

1. не более 20 страниц или прокруток;
2. остановка после двух итераций без увеличения DOM;
3. остановка при исчерпании каталога.

Короткий `asyncio.sleep(0.1)` используется только как пауза вежливости между итерациями, а не как способ дождаться данных.

### 4.3. Обработка ошибок

Для `PlaywrightTimeoutError` предусмотрено сохранение полноэкранного скриншота и HTML в `artifacts/`. Ошибка отражается в журнале. Остальные исключения не подавляются и приводят к неуспешному выполнению ячейки после освобождения ресурсов.

В успешном контрольном запуске диагностические артефакты не создавались, поскольку таймаутов не было.

## 5. Дешёвая альтернатива

После диагностики браузер для основного сбора не требуется:

- JS-каталог получен прямым запросом к `/ajax/products/json`;
- страницы пагинации получены обычными HTTP GET-запросами;
- порции бесконечной прокрутки получены через `/ajax/products?offset=...`.

HTML-порции разбираются через BeautifulSoup. Поскольку эндпоинт прокрутки возвращает пересекающиеся порции, внутри одного контекста записи дедуплицируются по `record_id`. Пустой ответ HTTP 204 является признаком окончания данных.

`data_light.csv` содержит те же 306 наблюдений, что и `data_browser.csv`:

- только в браузерном наборе: 0;
- только в HTTP-наборе: 0;
- расхождения цен: 0.

На этой небольшой странице одиночный замер не показал экономии времени и трафика: разброс сетевой задержки оказался больше потенциального выигрыша, а часть изображений загружается лениво. Для достоверной оценки ускорения нужны несколько повторов и медиана; в лабораторной приведены фактически полученные, а не ожидаемые значения.

## 8. Локаторы и устойчивость к редизайну

| Локатор | Обоснование | Смена CSS-класса | Дополнительный `div` | Перевод текста |
|---|---|---|---|---|
| `[data-testid="product-name"]` | Специальный тестовый атрибут | не влияет | не влияет | не влияет |
| `get_by_role("link", name="Next page")` | Семантическая роль и доступное имя | не влияет | не влияет | локатор потребуется изменить |
| `#end-of-page` | Уникальный sentinel прокрутки | не влияет, пока сохраняется `id` | не влияет | не влияет |

Классы `.product-item`, `.product-name` и `.product-price` являются читаемыми предметными классами, а не сгенерированными именами. При их переименовании массовое извлечение потребуется обновить. Вставка дополнительной обёртки не повлияет, поскольку поиск выполняется по потомкам карточки. Структурный XPath не используется.

Для ссылки следующей страницы более устойчивым вариантом был бы `a[rel="next"]`, однако на текущей учебной странице атрибут `rel` отсутствует.

## 10. Выводы и рекомендации

1. **Разовое исследование.** Playwright удобен, потому что показывает итоговый DOM, позволяет воспроизвести взаимодействия и обнаружить XHR.
2. **Ежедневный сбор 10 000 записей.** Следует использовать прямые JSON/HTML-запросы: они быстрее, требуют меньше памяти и трафика.
3. **Сайт с антибот-защитой.** В рамках этой работы обход защиты запрещён. Следует использовать разрешённый API, получить согласие владельца или отказаться от автоматического сбора. Playwright сам по себе не делает обход защиты допустимым.

## 11. Правовая и этическая оценка

Использована учебная площадка, предназначенная для практики веб-скрейпинга. Коммерческие сайты, реальные аккаунты, CAPTCHA и антибот-механизмы не обходились. Между итерациями добавлена небольшая пауза; число запросов ограничено предохранителями.

Собираются только тестовые сведения о товарах: название, цена и URL. Персональные данные отсутствуют, поэтому обработка персональных данных по 152-ФЗ в фактическом наборе не выполняется. При переносе решения на другой источник необходимо отдельно проверить правила сайта, `robots.txt`, условия использования, правовое основание сбора и наличие персональных данных.
